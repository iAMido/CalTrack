# CalTrack full QA: 20/10/2026 (after "CalTrack without Telegram")

Ido asked for "a full QA on CalTrack and the WhatsApp fix we just did; in-depth analysis making sure NOTHING is broken".
This is the record: what was tested, how, what was found, what was fixed, and how to run it again.

**Bottom line**
- The Telegram removal broke nothing: old and new code gave identical results on 42 of 42 shared steps.
- The deep QA found **5 bugs that were already there before 20/10**, and all are fixed. The worst: **every weekly coach report since September was cut mid-sentence.**
- The real database was **unchanged** after every run (fingerprint proof).

## 2. Method
All runs were in throwaway containers on the VPS (`--network host`, private ports 18089/18093), never the live bot.

- **`scripts/wa_deep_qa.py`.** Starts the real WhatsApp listener with a **fake gateway** that captures every `/send` and `/poll` and serves a real meal photo (downloaded read-only from Storage).
  - **Every database write is intercepted and recorded, never executed:**
    - `supabase_client.insert/upsert/update/delete_row/upload_photo`;
    - every `.insert/.update/.upsert/.delete` through `get_client().table(...)`;
    - Storage uploads.
  - Reads go to the real database, so answers are real.
- **`scripts/db_fingerprint.py`.** Row count + an md5 of the content of 14 tables, taken before and after each run. **Unchanged after every run.** Two back-to-back fingerprints match, so it's a valid proof.
- **A/B.** The same deep QA ran on the code from before 20/10 (commit `8186a62`, built as its own image with python-telegram-bot) and on the new code. A per-step diff compared message kinds, poll options, write targets, and text with digits masked; steps whose wording comes from an LLM were compared by structure only.
- **Infrastructure.** Gateway routing, the retry queue, a crash test, resources and logs.
- **TARS side.** `scripts/qa/run_all.sh` and `scripts/qa/day_flow.py` in the TARS repo (the gateway carries CalTrack's messages).

## 4. Findings
### Migration (Telegram removal): no regressions
A/B: **42 of 42** shared steps identical: every reply, every poll option, every write target.
The final diff differed **only** in the intended fixes below.

### Pre-existing bugs, found and fixed
| # | Bug | Effect | Fix |
|---|---|---|---|
| 1 | **The weekly coach report was cut mid-sentence**, every Saturday since September | Every saved report is ~4,950 chars, ending e.g. "**חטיף (10" or "2 בי". Hebrew used up `max_tokens: 3500` | `max_tokens: 9000`, plus a warning in the log if `finish_reason == "length"`. A full report is now ~10,500 chars (3 WhatsApp messages) and ends cleanly (#24) |
| 2 | **After `ברקוד` / `תווית`, CalTrack ignored commands** | `waiting_for=barcode` is in `AWAITING`, so a plain command ("מצב") went to the text-answer handler and was dropped. Silent until a photo or a `/command` | `server.Dispatcher.text`: while waiting for a photo, a command ends the wait and runs; other text gets "📷 מחכה לתמונה של…" (#23) |
| 3 | English item names after 🔄 / ➕ | "Turkey breast", "White rice": the typed Hebrew was translated before being stored as the display name | `callbacks.handle_text_input` keeps what Ido typed as `ingredient_name_he`; English is only for the lookup (#23) |
| 4 | Barcode / label / stats replies in English | "Send me a clear photo of the product barcode", "System Stats", "Target" | Hebrew rules in `bot/whatsapp/he.py` (#23) |
| 5 | Raw Markdown in the coach report | `#`, `##`, `**…**`, `---` don't render on WhatsApp | `gateway.markdown_to_whatsapp` inside `to_whatsapp` (#23) |

### Infrastructure checks
- **Crash recovery:** `kill -9` on the container's PID → `restart: unless-stopped` restarted it (RestartCount 0 → 1). All 5 jobs were rescheduled and the listener came back within seconds.
- **Gateway:** `WA_CALTRACK_JID` is set. The CalTrack forwarder has its own disk-backed retry queue (`~/.tars/wa/caltrack-queue.jsonl`, retried every 30 s), and its `retryLoop` is started. So a message sent while CalTrack restarts is delivered afterwards, and CalTrack de-duplicates it. Nothing was pending.
- **Resources:** ~52 MB of 768 MB, no errors in the logs since start.
- **TARS status panel:** checks `127.0.0.1:8093/wa/health`, not Telegram, and shows "ok, listening".
- **Packages:** python-telegram-bot is not installed in the live image; `tests/test_whatsapp.py::test_no_telegram_left` fails if anything imports `telegram`.

### TARS side
- `run_all.sh`: all green.
- `day_flow.py`: **23/23** after hardening four checks that were false alarms:
  - the model writes a group header with "—" instead of "-";
  - a to-do may be put on a list without asking;
  - no fresh voice note in the gateway cache;
  - Webtop signed out in the evening.
- The real 21:00 digest of 20/10 did report Shir's trip-volunteer poll at the top.

## 5. Mistakes during testing, and their clean-up (data)
The first smoke-test version ran `שבוע` and a typed meal against the real database:
- it **inserted a coach_reports row** (week 18–24/10, created 21:58);
- it **inserted a personal_foods row** ("toast").

Both were found and deleted by id, and their contents were checked first. The harnesses were then changed:
- `wa_smoke.py` never runs `שבוע` and stubs the learned-food write;
- `wa_deep_qa.py` intercepts **every** write.

A fingerprint after each later run proved no further writes.
**Rule:** never run a raw test against the real database without the write guard plus a before/after fingerprint.

## 6. How to run it again (on the VPS)
```bash
cd ~/caltrack && rm -rf /tmp/qa && git worktree add -q /tmp/qa HEAD
R="docker run --rm --network host --env-file /etc/caltrack/caltrack.env -v /tmp/qa:/app -w /app caltrack-caltrack:latest"
$R python tests/test_whatsapp.py                      # unit tests (ALL PASS)
$R python scripts/db_fingerprint.py > /tmp/fp1.json
$R python scripts/wa_deep_qa.py --json /app/qa.json   # ~12 min, real LLM calls, writes intercepted
$R python scripts/db_fingerprint.py > /tmp/fp2.json && cmp /tmp/fp1.json /tmp/fp2.json && echo "DB unchanged"
$R python scripts/wa_smoke.py /tmp/ct_smoke_baseline.json   # quick check vs a saved baseline
docker run --rm -v /tmp:/t caltrack-caltrack:latest rm -rf /t/qa; git worktree prune
```
Notes:
- The photo step waits for its poll (vision can be silent for 20 s+).
- If you send a photo while a meal card is open, the answer is the "meal open" hint, as designed.
